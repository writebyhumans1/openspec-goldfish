# Releasing Goldfish

Release from a clean checkout of the reviewed main revision. Node 22+ is supported for consumers; the OIDC publishing runner uses Node 24 and npm 11 (trusted publishing requires npm >=11.5.1 and Node >=22.14.0).

## Candidate checks

Open a reviewed PR for the intended changes. Automatic releases use a patch increment by default; set a larger stable version in package.json in the PR when a minor or major release is needed. Verify MIT licensing and repository/homepage metadata. Run `npm test`, `npm run check`, and `npm pack --dry-run` before merging. The package test installs a tarball into temporary roots for all three harnesses and both scopes.

Merging to main starts the automatic release described below. Do not manually tag or create a GitHub release to trigger publication. When a version bump is needed, the workflow opens a version PR and validates that exact candidate. After the PR is merged, it tags the merged revision, validates it again, and publishes.

## First publication

If no package exists, authenticate locally with `npm login` and check `npm whoami`. Never put tokens or OTP values in repository files or logs. Run the candidate checks above, then `npm publish --access public` from the clean candidate checkout. Complete any npm interactive authentication in the terminal. If authentication or publication fails, stop and record the remaining step; do not claim success.

The automatic workflow recognizes an existing bootstrap version only when its registry `gitHead` and MIT license match the checked revision; it does not republish that version. A local bootstrap is not an OIDC/provenance verification.

## Automatic releases from main

Every push to main (including a merged PR) runs `publish.yml`. If package.json already contains a stable version higher than the latest tag, the workflow tags that merged revision. Otherwise, it increments the highest stable tag's patch version, updates package.json and the bundled runtime version on a `release/v<version>-<sha>` branch, and opens a version PR. It never pushes to main. The candidate is tested before the PR is opened; the workflow also dispatches `test.yml` for the PR branch because GitHub does not start PR workflows for events created with the default `GITHUB_TOKEN`.

All six Node 22/24 Linux/macOS/Windows matrix entries must pass before npm publication. Merge the generated version PR to continue the release. The subsequent main push tags that merged revision, reruns the validation matrix, publishes to npm, and creates the GitHub release. Events generated by `GITHUB_TOKEN` do not trigger another publish workflow.

One-time setup:

- Permit GitHub Actions `contents: write`, `pull-requests: write`, and `actions: write` for the release workflow. The workflow pushes only release branches and tags; all main changes go through the generated version PR.
- In npm package settings configure GitHub Actions trusted publishing with owner `writebyhumans1`, repository `openspec-goldfish`, workflow `publish.yml`, no environment, and direct publish enabled. No npm token is required. The package repository metadata must match this repository.
- Use Node 24 and npm 11, as configured. See [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) for current requirements. Trust setup must be verified by a real successful release.

The manual workflow dispatch can recover a failed run. If a version PR is already open for the current main revision, preparation reuses its branch. After merging the PR, a main push resumes validation and publication. Registry verification permits an existing version only when its gitHead and MIT license match. Never delete or move a published tag. A tag may remain after a test or publishing failure; rerunning the workflow reuses it only when it points to the checked main revision.

## Verify the public release

Run `npm view openspec-goldfish@<version> version license gitHead repository homepage dist --json`. Confirm the registry revision and license, then run `npx --yes openspec-goldfish@<version> --harness <harness> --<scope>` in temporary directories for claude/codex/devin and local/global. Redirect global config to temporary roots with CLAUDE_CONFIG_DIR, CODEX_HOME, and XDG_CONFIG_HOME (APPDATA on Windows); never smoke-install over a user's configuration. Verify skill, agents, protocol, runtime and no unintended `openspec/` directory.

Record version, revision, CI outcomes, authentication mode, and smoke results in `docs/releases/<version>.md`. After verification, update README/site to remove pending wording in a follow-up PR. npm's registry README comes from the published tarball: update it in the next real package version, as described in [npm's README guidance](https://docs.npmjs.com/about-package-readme-files/); the GitHub README/site can be current immediately.

## GitHub Pages

Enable Pages in repository Settings -> Pages -> Source: GitHub Actions. The Pages workflow deploys only `website/` and the required logo from main or manual dispatch; PRs validate without deployment. Preview locally with `node scripts/build-site.mjs` then stage `.site/` beneath `/tmp/goldfish-preview/openspec-goldfish/` and run `python3 -m http.server 4173 --directory /tmp/goldfish-preview`. Verify the `/openspec-goldfish/` path, desktop/mobile layout, keyboard focus, clipboard success/failure, and readable content without JavaScript.

Verify https://mehdishahdoost.github.io/openspec-goldfish/ after deployment, including logo/styles, npm/repository/docs links and availability wording. Record the deployment revision and URL.

## Recovery

If publication has not happened, fix the candidate and repeat checks. A published version is immutable: release a corrected new version rather than relying on unpublish. If Pages fails, the npm release remains available; repair and redeploy the site or revert its source commit. Never overwrite earlier release records or claim an untested OIDC path has passed.
